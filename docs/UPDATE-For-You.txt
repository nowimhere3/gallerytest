> ## Browser Gallery — Development Update: 7.2 → 7.3 → Tag Persistence Debug
>
> ### Version 7.2 — Prompt 2 / Phase 1a
>
> **Gallery Thumbnail Click → Viewer + Gallery Reset**
>
> 7.2 added/improved Gallery thumbnail navigation.
>
> The intended behavior is now:
>
> **Click a Gallery thumbnail → select/load that media in Viewer → return the Gallery scroll position to the top.**
>
> This is deliberately a **single-click action**. The purpose is to eliminate the old workflow where someone could scroll hundreds of items down a large Gallery, click an item, and then have to manually navigate/scroll back to the Viewer.
>
> Importantly, this was designed to reuse the existing runtime/current-item selection architecture rather than creating another current-media/navigation state.
>
> The scroll reset is specifically supposed to target the appropriate Gallery/page scroll mechanism rather than blindly doing an arbitrary global scroll. Existing active-card highlighting, image/video handling, Favorites, Hidden, tag badges/filtering, lazy thumbnails, Presentation Mode, slideshow, shuffle, loop, and automation were explicitly required to remain intact. 
>
> ---
>
> ### Version 7.3 — Prompt 3 / Phase 2
>
> **Tags Status Update Center + Last Tag Position**
>
> 7.3 expanded the existing Tags/Fast Tagging system with **persistent tag activity/checkpoint metadata**.
>
> Each tag can now conceptually carry information such as:
>
> `lastTagPosition`
>
> representing the most recent sequential media position where that tag was **actively applied during Fast Tagging**.
>
> Example:
>
> `Feet — 400 / 1421 — Aug 6, 2026 · 11:42 PM`
>
> This is deliberately **not** simply "the last place the tag was clicked." It's intended as a checkpoint for working through very large media libraries.
>
> The Tags Settings layout was reorganized to:
>
> **1. Status Update Center**
> **2. New Tag**
> **3. Existing tag chips/cards**
>
> Clicking a tag inside Tags Settings only selects that tag for inspection and updates the Status Update Center. It must **not** navigate the Gallery, change the current media, populate Jump To, scroll anywhere, or start playback.
>
> During sequential Fast Tagging, **applying** a tag updates its activity metadata using the application's existing human-readable position semantics (`currentIndex + 1 / total`) plus timestamp. Removing a tag is not considered a new checkpoint.
>
> This metadata was deliberately made **Profile metadata**, using the existing ProfileStore/persistence architecture rather than introducing another database/storage system. It was required to survive reload/reopen and Profile Export/Import while remaining compatible with older profiles that don't contain this metadata. 
>

> ## Post-7.3 Debugging — Important Tag Persistence Bug
>
> After 7.3, we discovered that there are actually **two distinct pieces of persistent tag information**:
>
> **1. Tag vocabulary / definitions**
>
> Example:
>
> `tag-123 → "Funny"`
>
> **2. Per-media tag assignments**
>
> Example:
>
> `Animals/Cat.mp4 → tags: ["tag-123"]`
>
> IndexedDB persistence already stored both, so tags survived ordinary reload/reopening in the same browser/profile.
>
> However, we discovered the **Profile Export/Import path was not originally self-contained**.
>
> Item records could retain:
>
> `tags: ["tag-123"]`
>
> while the exported/imported Profile failed to restore the definition:
>
> `tag-123 → "Funny"`
>
> That created **dangling tag IDs**.
>
> The assignment technically still existed, but Gallery no longer knew what `tag-123` meant. Consequently the tag name couldn't be displayed correctly, the tag filter vocabulary couldn't be rebuilt, and the tagging UI appeared to have "lost" the tag.
>
> ### Fix
>
> Profile Export/Import was changed so the Profile contains **both the tag vocabulary and item records**.
>
> Conceptually:
>
> ```json
> {
>   "schemaVersion": 1,
>   "kind": "gallery-profile",
>   "exportedAt": "...",
>   "tags": [
>     { "id": "tag-123", "name": "Funny" }
>   ],
>   "items": {
>     "Animals/Cat.mp4": {
>       "favorite": true,
>       "tags": ["tag-123"]
>     }
>   }
> }
> ```
>
> Tag IDs remain stable rather than being regenerated.
>
> Import behavior was also made explicit:
>
> **Merge:** merge incoming vocabulary with existing vocabulary without duplicating definitions having the same tag ID.
>
> **Replace:** replace both the item profile **and tag vocabulary**, rather than replacing items while accidentally retaining unrelated old tags.
>
> Older Profile exports containing `items` but no `tags` remain valid and import without crashing.
>
> Existing Favorites, Hidden, `favoritedAt`, and unknown/open-shaped item fields must continue round-tripping unchanged.
>

> ## Second Bug Found During Verification — Async Replace Race
>
> After that initial fix, a subtler bug was discovered in `ProfileStore`.
>
> `ProfileStore` performs an asynchronous initial load from IndexedDB through `#loadSavedRecords()`.
>
> Replace-import already prevented **old item records** from being merged back into a newly replaced Profile.
>
> But the corresponding **old tag vocabulary was still being merged unconditionally**.
>
> This created a race:
>
> `new ProfileStore()`
>
> → initial IndexedDB load starts but hasn't completed
>
> → Replace Profile import occurs
>
> → imported vocabulary correctly replaces old vocabulary
>
> → delayed initial IndexedDB load completes
>
> → **old tags get merged back in**
>
> That violated Replace semantics.
>
> The narrow fix was made in:
>
> **`src/profile/profile-store.js`**
>
> Specifically, the startup tag-merge inside `#loadSavedRecords()` was given the same `#replaceBeforeLoad` protection already being used for item records.
>
> In effect:
>
> **Replace-before-initial-load means neither stale items nor stale tags may subsequently merge back in.**
>
> No redesign of Tags, ProfileStore, or IndexedDB was necessary.
>
> `src/profile/indexeddb.js` remained the persistence boundary and `src/main.js` continued interacting through ProfileStore rather than accessing IndexedDB directly.
>

> ## Verification Result
>
> Focused testing covered:
>
> * ordinary tag persistence/reload
> * tag vocabulary + item assignment Export → Import
> * fresh/empty Profile import
> * legacy item-only Profile imports
> * Merge with overlapping tag IDs
> * Replace removing unrelated vocabulary
> * stable tag IDs
> * Favorites/Hidden/`favoritedAt`
> * unknown/open-shaped item fields
> * deterministic delayed IndexedDB startup-load race
>
> These checks passed after the race protection was added.
>
> ### Current architectural rule
>
> **ProfileStore owns Profile state and behavior → existing IndexedDB layer persists it.**
>
> Tags should not get a second persistence mechanism, and callers such as `main.js` should not directly manipulate IndexedDB.
>
> ### Important distinction going forward
>
> Do not treat these as the same thing:
>
> **Tag definition:** `"Funny"` exists and has stable ID `tag-123`
>
> **Tag assignment:** media X references `tag-123`
>
> **Tag activity metadata:** checkpoint information such as the last sequential position/time where `tag-123` was actively applied.
>
> All three are related, but they represent different data and need to survive the appropriate Profile persistence/export/import lifecycle.

One thing I'd specifically tell the other AI: **7.3 didn't merely add "tags."** Tags/Fast Tagging already existed. 7.3 added the **activity/checkpoint layer on top of them**. The debugging afterward exposed that the underlying tag vocabulary itself wasn't being carried safely through the floppy-disk-style Profile Export/Import cycle. That's the important progression.
